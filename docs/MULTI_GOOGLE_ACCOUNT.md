# 두 번째 Google 계정 — 기기에 로그인하지 않고 쓸 수 있나

2026-09-26 검토. 계기는 A 계정의 Drive 용량이 가득 찬 것
(`docs/troubleshootings/project-specific/upload-403-storage-quota.md`).

요구는 둘이다.

1. 두 번째 계정을 **앱에만** 남기고 기기(안드로이드 계정 관리자)에는 로그인하지 않고 싶다.
2. 안 되면, Drive 의 공유 기능을 써서 **잠깐 로그인해 올리고 나중에 보는** 정도라도 되나.

## 1. 지금 구조에서는 안 된다

앱은 Play 서비스의 `AuthorizationClient` 를 쓰고, 계정을 `Account(email, "com.google")` 로 지정한다.
이 `com.google` 이 **안드로이드 계정 관리자에 등록된 계정**이다. 계정 선택 창에 뜨는 목록이 곧
*설정 → 계정* 의 목록이고, 그 창의 "계정 추가" 로 더해도 결국 기기에 로그인된다.

즉 **GMS 경로로는 기기 로그인 없이 토큰을 받을 방법이 없다.** 우회가 아니라 그 API 의 전제다.

## 2. 그래도 하려면 — 브라우저 OAuth (가능하지만 값이 비싸다)

Google 이 공식으로 지원하는 다른 길이 있다. RFC 8252(OAuth 2.0 for Native Apps) 방식으로,
**Chrome Custom Tab** 에서 인증하고 PKCE 로 코드를 교환한다. 이때 로그인은 **브라우저의 웹 세션**에서
일어나므로 기기 계정 관리자에는 아무것도 추가되지 않는다. 요구 1을 만족한다.

대신 지금 설계에서 세 가지가 뒤집힌다.

| | 지금 | 브라우저 OAuth |
|---|---|---|
| 클라이언트 ID | 앱에 심지 않는다(패키지명 + SHA-1 로만 식별) | **앱에 심는다** (PKCE 라 secret 은 없어도 된다) |
| 토큰 보관 | Play 서비스가 한다 | **우리가 한다** — refresh token 을 암호화 저장하고 갱신까지 |
| 인증 경로 | 하나 | 둘 (기존 계정은 GMS, 새 계정은 브라우저) |

`CLAUDE.md` 가 "Google 인증은 `AuthorizationClient` 만" 으로 못 박아 둔 것이 이 지점이다.
규칙을 바꾸는 결정이지 코드만 더하는 일이 아니다.

### 2.1 발을 걸 만한 것

- **게시 상태가 "테스트" 인 동안 refresh token 이 7일 만에 만료된다.** Google 의 문서화된 정책이고,
  프로덕션으로 게시해야 풀린다. 브라우저 OAuth 는 refresh token 으로 버티는 방식이라 이게 직격이다 —
  **일주일마다 다시 로그인**하게 된다. (GMS 경로도 같은 제약을 받지만 그쪽은 재동의를 알아서 띄운다.)
- Chrome 에 이미 로그인돼 있으면 "다른 계정 사용" 이 **Chrome 계정 설정으로 빠지고 앱으로 돌아오지
  않는** 사례가 AppAuth 이슈로 보고돼 있다. 우리가 원하는 "기기와 무관한 계정" 흐름에서 정확히 밟는 길이다.
- Chrome 137+ 의 Auth Tab 이 이 문제를 줄이지만, 그 미만 기기는 Custom Tab 폴백이다.

### 2.2 판단

**지금은 권하지 않는다.** 프로덕션 게시 전에는 7일 만료 때문에 실사용이 안 되고, 얻는 것은
"기기에 계정을 추가하지 않는다" 하나다. 앱을 프로덕션으로 올린 뒤에 다시 볼 문제다.

## 3. 공유로 되는 것과 안 되는 것 — 먼저 사실 하나

**파일을 올린 사람이 그 파일의 주인이고, 용량은 주인에게 매겨진다.**

B 가 폴더를 A 에게 편집 권한으로 공유해도, **A 가 올린 파일은 A 소유**라 **A 의 용량을 먹는다.**
"B 의 폴더에 올리면 B 의 용량을 쓴다" 는 성립하지 않는다. 그게 되는 것은 Workspace 유료의
**공유 드라이브(Shared Drive)** 뿐이고, 개인 Gmail 계정에는 없다.

그러므로 **B 의 저장 공간을 쓰려면 올리는 주체가 B 여야 한다.** 우회가 없다.
(A 가 올린 뒤 소유권을 B 로 넘기는 방법도 A 의 용량이 비어 있어야 올릴 수 있으므로,
"A 가 꽉 찼다" 는 지금 상황에서는 출발점부터 막힌다.)

## 4. 그래서 실제로 되는 조합

올리는 것과 보는 것을 **떼어 놓으면** 요구 2가 성립한다.

```
① B 를 기기에 잠깐 추가 → 앱을 B 로 연결 → B 의 폴더 F 에 업로드   (용량은 B 가 낸다)
② B 가 F 를 A 에게 공유                                         (Drive 앱에서 한 번)
③ B 를 기기에서 제거 → 앱을 A 로 되돌림
④ A 로 F 를 "볼 수 있는 폴더" 에 추가 → 앱에서 사진이 보인다      (drive.readonly, §10)
```

핵심은 ④다. 지난번에 넣은 **보기 전용 폴더**(`docs/DRIVE_FILE_SCOPE.md` §10)가 이걸 가능하게 한다.
`drive.readonly` 는 **사용자가 읽을 수 있는 모든 파일**을 덮으므로 **공유받은 파일도 포함**된다.
`drive.file` 만 있을 때는 불가능했다.

즉 **B 는 업로드하는 순간에만 기기에 있으면 되고, 그 뒤로는 A 만으로 계속 본다.**
요구 1을 100% 만족하지는 못하지만(업로드 시점에는 기기 로그인이 필요하다) 가장 가까운 답이다.

### 4.1 이걸 되게 하려면 손봐야 하는 것

| # | 무엇 | 왜 |
|---|---|---|
| 1 | 보기 전용 폴더 피커에 **"공유 문서함"** 을 더한다 | 지금은 `'root' in parents` 만 훑는다. 공유받은 폴더는 내 루트에 없어서 **목록에 안 뜬다** (`sharedWithMe = true` 로 따로 물어야 한다) |
| 2 | 업로드 원장이 **Google 계정을 구분**하게 한다 | 지금은 Drive 를 계정 하나로 보고 전부 `accountId = null` 로 적는다. A↔B 를 오가면 B 에 없는 사진이 "이미 백업됨" 으로 제외된다 |
| 3 | 계정을 바꿔도 **폴더 설정이 살아남게** 한다 | 연결 해제가 업로드 폴더·지정 폴더·보기 폴더를 전부 지운다. 오갈 때마다 다시 지정해야 한다 |

2·3 은 계정을 오가는 이상 어떤 방식을 택하든 필요하다. **여기가 먼저다.**

## 5. 일회성 브라우저 로그인 — "잠깐 로그인해서 올리고 닫는다"

2026-09-26 추가 검토. §2 의 브라우저 OAuth 를 **토큰을 남기지 않는 방식**으로 쓰면
§2.1 의 가장 큰 걸림돌이 사라진다.

```
"다른 계정으로 올리기" → 일회용 브라우저 탭에서 B 로 로그인 → 탭이 닫힘
  → access token(1시간)만 받아 업로드 → 끝나면 버린다
```

### 5.1 왜 이러면 되는가

| §2 의 문제 | 일회성이면 |
|---|---|
| 테스트 상태에서 refresh token 7일 만료 | **refresh token 을 받지 않는다**(`access_type=offline` 을 빼면 아예 안 온다). 7일 규칙은 refresh token 에만 걸린다 |
| 토큰을 우리가 오래 보관해야 한다 | 최대 1시간짜리 access token 뿐이다. 새면 1시간 안에 스스로 무효가 된다 |
| 기기에 계정이 남는다 | 안드로이드 계정 관리자는 건드리지 않는다 |
| **Chrome 에 B 의 세션이 남는다** | **Ephemeral Custom Tab** 으로 연다 — 쿠키·기록이 그 탭 안에만 있고 닫으면 지워진다 |

마지막 줄이 중요하다. 일반 Custom Tab 은 Chrome 과 쿠키를 공유해서, 로그인하면 **B 가 Chrome 에
로그인된 채로 남는다.** "기기에 다른 계정을 남기고 싶지 않다" 는 요구를 거기서 어긴다.
Ephemeral Custom Tab(`androidx.browser` 1.8.0+, `setEphemeralBrowsingEnabled(true)`,
Chrome 136+)은 탭을 닫는 순간 흔적을 지운다. 우리 테스트 기기 둘 다 Chrome 153 이다(2026-09-26 확인).

### 5.2 사람이 해야 하는 일

1. **B 를 OAuth 동의 화면의 테스트 사용자에 추가.** 게시 상태가 테스트면 목록에 있는 계정만 로그인된다.
2. ~~Android OAuth 클라이언트의 "Custom URI scheme" 을 켠다~~ — **2026-09-27 정정, §6.2 참고.**
   Google 의 현행 문서는 "Custom URI scheme 은 Android 에서 더 이상 지원하지 않는다" 고 적고 있다.
   2023년 공지는 "새 클라이언트는 기본 꺼짐, 고급 설정에서 켤 수 있음" 이었는데, 그 뒤로 더 닫혔다.
3. **`CLAUDE.md` 의 "Google 인증은 `AuthorizationClient` 만" 을 고친다.** 인증 경로가 둘이 된다 —
   주 계정은 지금처럼 GMS, 일회성 계정은 브라우저.

### 5.3 제약

- **한 번 로그인에 1시간.** 업로드가 장당 0.7초면 시간당 약 5,000장이라 대부분의 배치는 들어간다.
  긴 영상이 섞여 1시간을 넘기면 남은 것은 "다시 로그인하면 이어서 올립니다" 로 멈춘다.
- **앱이 죽으면 토큰도 사라진다.** 메모리에만 두면 백그라운드 업로드 중 프로세스가 죽을 때 끊긴다.
  만료 시각과 함께 암호화해 두되 **refresh token 은 절대 저장하지 않는다** — 새어도 1시간이다.
- **나중에 보려면 다시 로그인해야 한다.** 토큰을 남기지 않으니까. 로그인 없이 보려면 §4 처럼
  B 가 A 에게 폴더를 공유하고 A 에서 보기 전용 폴더로 본다.
- B 로 로그인할 때마다 "확인되지 않은 앱" 경고와 동의 화면을 지난다(테스트 상태인 동안).

### 5.4 선행 작업

§4.1 의 **2(원장을 계정별로)** 는 여기서도 필요하다. B 로 올린 것을 A 의 기록에 섞으면
A 로 돌아왔을 때 A 에 없는 사진이 "이미 백업됨" 으로 빠진다. 일회성 세션은 로그인 직후
Drive `about` 으로 이메일을 받아 그 이메일로 원장에 적는다.

## 6. "다른 계정 업로드" — 주 계정은 그대로 두고 잠깐만

2026-09-27 검토. 요구가 더 구체적이 됐다.

> A 는 연결된 채로 둔다. "다른 계정 업로드" 를 누르면 잠깐 B 로 로그인해 올리고,
> A 에게 공유까지 한 뒤, B 는 풀린다. **연결 해제는 하지 않는다.**

**된다.** 네 조각으로 나눠 보면 셋은 막힘이 없고, **B 로 로그인하는 한 조각**만 선택이 필요하다.

| 조각 | 되나 | 근거 |
|---|---|---|
| ① B 의 토큰을 **A 를 건드리지 않고** 받기 | 된다 — 방법은 §6.1 | 토큰 요청마다 계정을 따로 지정한다. A 의 연결 정보는 그대로 둔다 |
| ② B 의 Drive 에 올리기 | 된다 | 올린 사람(B)이 주인이라 **용량은 B 가 낸다**(§3) |
| ③ B 의 폴더를 A 에게 공유 | 된다 | `permissions.create` 는 `drive.file` 로 허용된다 — 앱이 만든 폴더라서. 폴더를 **한 번** 공유하면 안에 들어오는 파일은 모두 권한을 물려받는다. 알림 메일은 `sendNotificationEmail=false` 로 끈다 |
| ④ A 에서 보기 | 된다 — 이미 만들었다 | 보기 전용 폴더 + 공유 문서함(`DRIVE_FILE_SCOPE.md` §10.9). 공유한 폴더 ID 를 알고 있으니 **A 의 보기 폴더에 자동으로 더할** 수도 있다 |
| ⑤ 끝나면 B 를 푼다 | 된다 | 토큰을 버린다. **revoke 는 부르지 않는다** — §6.3 |

올린 기록은 `drive:<B 이메일>` 로 남는다(`docs/plans/ledger-per-account`). A 로 돌아와도 A 의 백업 표시는
섞이지 않고, 다음에 또 "다른 계정 업로드" 를 하면 B 에 이미 있는 것은 건너뛴다. **지난번에 원장을 계정별로
나눈 것이 이 기능의 전제였다.**

### 6.1 B 로 로그인하는 두 길

| | (가) Play 서비스 | (나) 브라우저 |
|---|---|---|
| B 가 기기에 | **있어야 한다**(업로드하는 동안) | 없다 |
| Google 이 지원하나 | 지원한다 — 지금 쓰는 그 API | **Android 쪽 돌아오는 길을 닫았다**(§6.2) |
| 백그라운드 업로드 | 앱이 죽어도 토큰을 다시 받아 이어간다 | 토큰이 1시간·메모리뿐이라 끊기면 다시 로그인 |
| 코드 | 적다 — 계정만 바꿔 `authorize` | 많다 — 인증 경로 하나를 새로 만든다 |
| `CLAUDE.md` 규칙 | 그대로 | 바꿔야 한다 |

(가)는 `AuthorizationRequest.setAccount(B)` 로 토큰을 한 번 받는 것이다. Play 서비스에는 "주 계정" 개념이
없어서, A 의 연결 정보(`accountEmail`)를 건드리지 않고 B 의 토큰만 따로 받을 수 있다. 다만 계정 선택 창에는
**기기에 로그인된 계정만** 나오고, 없으면 "계정 추가" 로 기기에 넣어야 한다. 앱이 기기 계정을 지울 수는
없으므로 끝난 뒤 빼려면 사용자가 *설정 → 계정* 에서 직접 지운다.

### 6.2 브라우저 길이 막힌 이유 — §5 정정

브라우저에서 인증한 뒤 **앱으로 돌아오는 방법**이 필요하다. 후보를 다 보면:

| 돌아오는 방법 | 상태 |
|---|---|
| Custom URI scheme(`com.jjw.easygallery:/oauth2redirect`) | Google 현행 문서: **"Android 에서 더 이상 지원하지 않는다"** |
| Loopback(`http://127.0.0.1:포트`) | "데스크톱 앱" 클라이언트용이다. 안드로이드 앱이 그 클라이언트를 쓰는 것은 정책상 회색 |
| https + App Link | "웹" 클라이언트가 필요하고 토큰 교환에 **client secret** 을 요구한다. 앱에 심으면 비밀이 아니다. 도메인과 `assetlinks.json` 도 필요하다 |

셋 다 지금 기대어 짓기 어렵다. §5 는 "Custom URI scheme 을 켜면 된다" 고 했는데 그 전제가 틀렸다.

### 6.3 끝낼 때 revoke 를 부르지 않는 이유

Google 의 revoke 는 그 토큰 하나가 아니라 **그 사용자에게 준 이 프로젝트의 모든 권한**을 지운다. B 로 부르면
다음번에 B 는 동의부터 다시 해야 하고, 앱이 지난번 B 의 Drive 에 만든 폴더를 다시 찾을 수 있을지도
보장되지 않는다(`drive.file` 은 부여 단위의 접근이다). access token 은 어차피 1시간 뒤 스스로 죽는다.
**버리기만 한다.**

### 6.4 판단

- **B 가 업로드하는 동안 기기에 있어도 된다면 → (가).** Google 이 지원하는 길이고 코드가 적고
  백그라운드 업로드도 끊기지 않는다. S23+ 처럼 이미 여러 계정이 있는 기기라면 추가 로그인도 없다.
- **B 가 기기에 한순간도 있으면 안 된다면 → 지금은 만들지 않는다.** (나)는 Google 이 Android 의 돌아오는 길을
  닫아서, 남은 방법이 전부 정책 회색이거나 도메인·비밀키가 필요하다.

## 7. 권고

**(A) 원장·설정을 계정별로 나눈다 + 피커에 공유 문서함을 더한다.** §4.1 의 1~3.
이것만 하면 §4 의 흐름이 돌고, 브라우저 OAuth 로 가더라도 그대로 쓰인다.

**(B) 앱 안에서 Drive 계정 여러 개를 등록해 고르기** 는 그다음이다. S3·WebDAV 가 이미 그 구조라
Drive 를 거기에 맞추는 일이고, (A) 를 해두면 자연스럽게 이어진다. 다만 **기기 로그인은 여전히 필요하다.**

**(C) 브라우저 OAuth 를 상시 로그인으로** 쓰는 것은 프로덕션 게시 이후로 미룬다. §2.1 의 7일 만료 때문이다.

**(D) 일회성 브라우저 로그인(§5)** 은 **보류한다**(2026-09-27). Google 이 Android 에서 브라우저 인증 뒤
앱으로 돌아오는 길(Custom URI scheme)을 닫았다 — §6.2.

**(E) "다른 계정 업로드"(§6)** 는 (A)(원장 분리, 2026-09-26 완료) 위에 **Play 서비스 길**로 얹는다.
조건은 하나 — 업로드하는 동안 B 가 기기에 있어도 되는가.
