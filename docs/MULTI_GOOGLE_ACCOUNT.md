# 두 번째 Google 계정 — 기기에 로그인하지 않고 쓸 수 있나

2026-09-26 검토. 계기는 A 계정의 Drive 용량이 가득 찬 것
(`docs/troubleshootings/project-specific/upload-403-storage-quota.md`).

요구는 둘이다.

1. 두 번째 계정을 **앱에만** 남기고 기기(안드로이드 계정 관리자)에는 로그인하지 않고 싶다.
2. 안 되면, Drive 의 공유 기능을 써서 **잠깐 로그인해 올리고 나중에 보는** 정도라도 되나.

## 1. 지금 구조에서는 안 된다

앱은 Play 서비스의 `AuthorizationClient` 를 쓰고, 계정을 `Account(email, "com.google")` 로 지정한다.
이 `com.google` 이 **안드로이드 계정 관리자에 등록된 계정**이다. 계정 선택 창에 뜨는 목록이 곧
*설정 → 계정* 의 목록이고, 그 창의 "계정 추가" 로 더해도 결국 기기에 로그인된다.

즉 **GMS 경로로는 기기 로그인 없이 토큰을 받을 방법이 없다.** 우회가 아니라 그 API 의 전제다.

## 2. 그래도 하려면 — 브라우저 OAuth (가능하지만 값이 비싸다)

Google 이 공식으로 지원하는 다른 길이 있다. RFC 8252(OAuth 2.0 for Native Apps) 방식으로,
**Chrome Custom Tab** 에서 인증하고 PKCE 로 코드를 교환한다. 이때 로그인은 **브라우저의 웹 세션**에서
일어나므로 기기 계정 관리자에는 아무것도 추가되지 않는다. 요구 1을 만족한다.

대신 지금 설계에서 세 가지가 뒤집힌다.

| | 지금 | 브라우저 OAuth |
|---|---|---|
| 클라이언트 ID | 앱에 심지 않는다(패키지명 + SHA-1 로만 식별) | **앱에 심는다** (PKCE 라 secret 은 없어도 된다) |
| 토큰 보관 | Play 서비스가 한다 | **우리가 한다** — refresh token 을 암호화 저장하고 갱신까지 |
| 인증 경로 | 하나 | 둘 (기존 계정은 GMS, 새 계정은 브라우저) |

`CLAUDE.md` 가 "Google 인증은 `AuthorizationClient` 만" 으로 못 박아 둔 것이 이 지점이다.
규칙을 바꾸는 결정이지 코드만 더하는 일이 아니다.

### 2.1 발을 걸 만한 것

- **게시 상태가 "테스트" 인 동안 refresh token 이 7일 만에 만료된다.** Google 의 문서화된 정책이고,
  프로덕션으로 게시해야 풀린다. 브라우저 OAuth 는 refresh token 으로 버티는 방식이라 이게 직격이다 —
  **일주일마다 다시 로그인**하게 된다. (GMS 경로도 같은 제약을 받지만 그쪽은 재동의를 알아서 띄운다.)
- Chrome 에 이미 로그인돼 있으면 "다른 계정 사용" 이 **Chrome 계정 설정으로 빠지고 앱으로 돌아오지
  않는** 사례가 AppAuth 이슈로 보고돼 있다. 우리가 원하는 "기기와 무관한 계정" 흐름에서 정확히 밟는 길이다.
- Chrome 137+ 의 Auth Tab 이 이 문제를 줄이지만, 그 미만 기기는 Custom Tab 폴백이다.

### 2.2 판단

**지금은 권하지 않는다.** 프로덕션 게시 전에는 7일 만료 때문에 실사용이 안 되고, 얻는 것은
"기기에 계정을 추가하지 않는다" 하나다. 앱을 프로덕션으로 올린 뒤에 다시 볼 문제다.

## 3. 공유로 되는 것과 안 되는 것 — 먼저 사실 하나

**파일을 올린 사람이 그 파일의 주인이고, 용량은 주인에게 매겨진다.**

B 가 폴더를 A 에게 편집 권한으로 공유해도, **A 가 올린 파일은 A 소유**라 **A 의 용량을 먹는다.**
"B 의 폴더에 올리면 B 의 용량을 쓴다" 는 성립하지 않는다. 그게 되는 것은 Workspace 유료의
**공유 드라이브(Shared Drive)** 뿐이고, 개인 Gmail 계정에는 없다.

그러므로 **B 의 저장 공간을 쓰려면 올리는 주체가 B 여야 한다.** 우회가 없다.
(A 가 올린 뒤 소유권을 B 로 넘기는 방법도 A 의 용량이 비어 있어야 올릴 수 있으므로,
"A 가 꽉 찼다" 는 지금 상황에서는 출발점부터 막힌다.)

## 4. 그래서 실제로 되는 조합

올리는 것과 보는 것을 **떼어 놓으면** 요구 2가 성립한다.

```
① B 를 기기에 잠깐 추가 → 앱을 B 로 연결 → B 의 폴더 F 에 업로드   (용량은 B 가 낸다)
② B 가 F 를 A 에게 공유                                         (Drive 앱에서 한 번)
③ B 를 기기에서 제거 → 앱을 A 로 되돌림
④ A 로 F 를 "볼 수 있는 폴더" 에 추가 → 앱에서 사진이 보인다      (drive.readonly, §10)
```

핵심은 ④다. 지난번에 넣은 **보기 전용 폴더**(`docs/DRIVE_FILE_SCOPE.md` §10)가 이걸 가능하게 한다.
`drive.readonly` 는 **사용자가 읽을 수 있는 모든 파일**을 덮으므로 **공유받은 파일도 포함**된다.
`drive.file` 만 있을 때는 불가능했다.

즉 **B 는 업로드하는 순간에만 기기에 있으면 되고, 그 뒤로는 A 만으로 계속 본다.**
요구 1을 100% 만족하지는 못하지만(업로드 시점에는 기기 로그인이 필요하다) 가장 가까운 답이다.

### 4.1 이걸 되게 하려면 손봐야 하는 것

| # | 무엇 | 왜 |
|---|---|---|
| 1 | 보기 전용 폴더 피커에 **"공유 문서함"** 을 더한다 | 지금은 `'root' in parents` 만 훑는다. 공유받은 폴더는 내 루트에 없어서 **목록에 안 뜬다** (`sharedWithMe = true` 로 따로 물어야 한다) |
| 2 | 업로드 원장이 **Google 계정을 구분**하게 한다 | 지금은 Drive 를 계정 하나로 보고 전부 `accountId = null` 로 적는다. A↔B 를 오가면 B 에 없는 사진이 "이미 백업됨" 으로 제외된다 |
| 3 | 계정을 바꿔도 **폴더 설정이 살아남게** 한다 | 연결 해제가 업로드 폴더·지정 폴더·보기 폴더를 전부 지운다. 오갈 때마다 다시 지정해야 한다 |

2·3 은 계정을 오가는 이상 어떤 방식을 택하든 필요하다. **여기가 먼저다.**

## 5. 권고

**(A) 원장·설정을 계정별로 나눈다 + 피커에 공유 문서함을 더한다.** §4.1 의 1~3.
이것만 하면 §4 의 흐름이 돌고, 브라우저 OAuth 로 가더라도 그대로 쓰인다.

**(B) 앱 안에서 Drive 계정 여러 개를 등록해 고르기** 는 그다음이다. S3·WebDAV 가 이미 그 구조라
Drive 를 거기에 맞추는 일이고, (A) 를 해두면 자연스럽게 이어진다. 다만 **기기 로그인은 여전히 필요하다.**

**(C) 브라우저 OAuth** 는 프로덕션 게시 이후로 미룬다. §2.1 의 7일 만료 때문에 지금은 실사용이 안 된다.
