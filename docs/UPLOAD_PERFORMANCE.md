# 업로드 속도 — 무엇이 느렸고 무엇을 바꿨나

100장, 1000장을 올릴 때도 쓸 만해야 한다. 이 문서는 **측정한 것**과 **그래서 고른 것**을 적는다.

## 1. 측정 (2026-09-25, Galaxy S23+, Wi-Fi)

145KB PNG 192장을 순차로 올리며 구간을 쟀다.

| 구간 | 시간 |
|---|---|
| 길이 조회 | 7ms |
| **세션 생성 (POST)** | **1,100ms** |
| **본문 전송 (PUT)** | **2,300ms** |
| 마무리(DB·원장) | 7ms |
| 합계 | **3,400ms / 장** |

장당 3.3초가 거의 일정했다(중앙값 3.28s, 최소 2.87s). **파일 크기와 무관하다** —
145KB 를 Wi-Fi 로 보내는 시간은 무시할 수준이고, 3.3초는 대부분 **왕복 대기**다.

DB 와 알림은 합쳐서 14ms 였다. 여기를 손대봐야 의미가 없다.

이 속도라면 100장에 5.5분, 1000장에 55분이다. 쓸 수 없다.

## 2. 고른 것

### 2-1. 작은 파일은 왕복을 한 번으로 (multipart)

Drive 는 `uploadType=multipart` 로 메타데이터와 본문을 **한 번의 POST** 에 보낼 수 있다.
세션 생성 1.1초가 통째로 사라진다.

대신 **중간에 끊기면 처음부터**다. resumable 의 이어올리기를 포기하는 것이다.
그래서 경계를 둔다 — **4MB 이하만** multipart, 그보다 크면 지금처럼 resumable.
4MB 를 다시 올리는 비용은 세션 왕복 한 번을 아끼는 값보다 작다. 영상은 대부분
이 선을 넘으므로 영향을 받지 않는다.

### 2-2. 동시에 여러 장 (병렬 4)

장당 3.3초 중 실제로 바이트가 흐르는 시간은 아주 짧다. 나머지는 서버를 기다리는
시간이라, 기다리는 동안 다른 파일을 보내면 그대로 처리량이 는다.

**동시 4개**로 정했다. 근거는 셋이다.

- Drive API 의 사용자당 요청 한도는 넉넉하다(100초당 수천 건). 4 동시는 초당 2건 남짓이라 멀다.
- OkHttp 의 호스트당 기본 동시 요청이 5다. 그 안에 있으면 커넥션 풀이 재사용된다.
- 모바일에서 동시 연결을 더 늘리면 대역폭을 나눠 쓰느라 개별 파일이 느려지고,
  실패했을 때 한꺼번에 재시도가 몰린다.

8, 16 으로 올리면 숫자는 더 나올 수 있지만, 종량제 회선과 약한 신호에서 역효과가 크다.
**4는 이득의 대부분을 가져오면서 위험이 적은 지점이다.**

### 2-3. 큐를 원자적으로 집는다

병렬이 되면 두 코루틴이 같은 항목을 집을 수 있다. `claimNext()` 를 트랜잭션으로 만들어
**PENDING 을 RUNNING 으로 바꾸면서 가져온다**. 이미 RUNNING 인 것은 건너뛴다.

앱이 죽어 RUNNING 인 채 남은 항목은 워커가 시작할 때 PENDING 으로 되돌린다.
그러지 않으면 영원히 집히지 않는다.

## 3. 고르지 않은 것

| 안 | 왜 안 했나 |
|---|---|
| 동시 8~16 | 위 2-2. 종량제·약전계에서 역효과. 얻는 것보다 잃는 것이 크다 |
| 모든 파일 multipart | 큰 영상이 끊기면 처음부터. 이어올리기를 버릴 수 없다 |
| 배치 API (`/batch`) | Drive 의 배치는 **업로드 본문을 담지 못한다**. 메타데이터 전용이라 여기엔 쓸 수 없다 |
| 진행률 DB 갱신 줄이기 | 이미 1초 스로틀이고 측정상 7ms. 손댈 이유가 없다 |

## 4. 측정하고 나서 고친 것

설계대로 만들고 실기기에서 돌리자 **문서가 틀렸던 곳이 두 군데** 나왔다.

### 4-1. 한 건의 타임아웃이 전체를 세웠다

165장 중 1장이 `SocketTimeoutException` 을 냈을 뿐인데 워커가 통째로 멈추고
백오프에 들어갔다(`succeeded=162 failed=0` 에서 중단). 순차일 때는 자연스러운
설계였지만 — 어차피 한 줄로 처리하니까 — 병렬에서는 나머지 수백 장이 남의 실패를
함께 기다리게 된다.

일시 오류는 **그 항목만 미뤄두고 계속 간다**. 미뤄둔 것이 남아 있으면 큐를 다 비운 뒤에
`Result.retry()` 를 돌려준다. 로그인 필요는 다르다 — 모든 항목이 같은 이유로 실패할
것이므로 그때는 즉시 멈춘다.

### 4-2. 한도 초과를 영구 실패로 버렸다

병렬 4로 올리자 Drive 가 `403 User rate limit exceeded` 를 돌려줬다. 그런데 워커는
**4xx 를 전부 영구 실패로** 분류하고 있었다. 다시 하면 되는 오류인데 큐에서 버려져,
사용자는 "몇 장이 안 올라갔다" 를 겪는다.

`403 + 한도 문구` 와 `429` 를 재시도 대상으로 분리했다(`RemoteStorageException.isRateLimited`).
한도에 걸린 코루틴은 1초부터 두 배씩 쉬었다가 다시 집는다 — 곧바로 다음 항목으로 넘어가면
그것도 같은 한도에 걸린다. 넷 중 하나씩 쉬면서 전체 속도가 저절로 조절된다.

### 4-3. 토큰이 만료되면 그 파일이 영영 빠졌다

1051장을 12분에 걸쳐 올리자 중간에 `401 invalid authentication credentials` 가 나왔다.
토큰 수명(45분)보다 짧은 실행이었지만 Play 서비스가 준 토큰이 먼저 만료된 것이다.
**401 도 4xx 라 영구 실패로 버려졌다.**

두 겹으로 고쳤다.

`TokenAuthenticator` 는 401 에 토큰을 새로 받아 한 번 재시도한다. 그런데
`invalidateToken()` 이 **우리 캐시만 비우고 Play 서비스 캐시는 그대로** 뒀다. 그래서
같은 만료 토큰을 다시 받아 또 401 이 나고, 두 번째라 포기했다. 이제 방금 거부된 토큰과
같은 것이 돌아오면 `clearToken` 으로 GMS 캐시까지 비우고 다시 받는다.

그리고 안전망으로 401 을 `isRetryable` 에 넣었다. 인증이 순간적으로 어긋나도
그 파일만 조용히 빠지는 일은 없어야 한다.

### 4-4. 앱이 죽으면 같은 파일이 두 벌 올라갔다

정리하다 Drive 에서 `k_0450.png` 가 **두 개** 나왔다. 강제 종료 테스트 때 생긴 것이다.

resumable 은 세션 URI 를 들고 있어서 되살아나면 그 세션을 이어받는다. 그런데
multipart 에는 세션이 없다. 올리는 도중 앱이 죽으면 **서버에는 파일이 생겼는데
우리 기록만 없는** 상태가 되고, 되살아난 워커가 그냥 다시 올려 두 벌이 된다.
속도를 얻으면서 재개를 버린 대가였고, 설계할 때 보지 못했다.

되살아난 항목만 올리기 전에 서버에 묻는다 — 같은 `mediaStoreId` 표식을 가진 파일이
그 폴더에 있는지. `releaseRunning()` 이 RUNNING 을 되돌릴 때 `attemptCount` 를 올리므로
"한 번 시도했던 것" 을 구분할 수 있다. 처음 올리는 항목은 묻지 않아 평소 속도는 그대로다.

80장을 올리다 21장째에 강제 종료했더니 `already on server, skipping` 이 **4건**
찍혔다 — 그 순간 진행 중이던 병렬 수와 정확히 같다. Drive 에 중복은 없었다.

이 넷을 고친 뒤 663장·1051장에서 **한도 초과 0건, 영구 실패 0건, 중복 0건**이었다.

## 5. 결과 (2026-09-26, 663장)

| | 전 | 후 |
|---|---|---|
| 장당 | 3.32s | **약 0.62s** |
| 100장 | 5.5분 | **1.0분** |
| 663장 | 37분 | **6.6분** |
| 1051장(실측) | 58분 | **12.2분** |

**4.8~5.3배.** multipart 가 1.3배, 병렬 4가 나머지를 가져왔다.
1051장은 733초, 장당 0.70초였다(663장 때는 0.62초 — 규모가 커져도 거의 선형이다).

같은 실행에서 확인한 것:

- 업로드된 파일 ID **중복 0** — 두 코루틴이 같은 항목을 집지 않는다
- 한도 초과 0, 영구 실패 0, 일시 실패 0
- 4MB 초과 7건은 resumable 경로로 갔다(PUT 17~28초). 두 경로가 크기로 갈린다
- **취소**하면 네 코루틴이 모두 멈추고 더 올라가지 않는다
- **앱을 강제 종료**해도 WorkManager 가 워커를 되살리고, `releaseRunning()` 이
  RUNNING 으로 남은 항목을 PENDING 으로 되돌려 이어서 올린다

기기 확인 항목은 `docs/manual-tests/02-google-drive.md` UPL-19~28.

## 6. 측정하면서 알게 된 것

**병렬은 공짜가 아니다.** 순차일 때는 드러나지 않던 것이 셋 나왔다 — 한 건의 실패가
전체를 세우고(4-1), 요청 한도에 닿고(4-2), 토큰 만료가 한 파일을 삼켰다(4-3).
셋 다 "4xx 면 영구 실패" 라는 한 줄에서 비롯됐다. 처리량을 올리면 **드물던 오류가
자주 일어나고**, 드물 때는 견딜 만했던 처리 방식이 문제가 된다.

**속도보다 분류가 중요했다.** multipart 와 병렬로 5배를 얻었지만, 그것만 했다면
1000장 중 몇 장이 조용히 빠지는 앱이 됐을 것이다. 사용자는 5배 빠른 것보다
"올렸다고 했는데 없는" 것을 먼저 알아챈다.
