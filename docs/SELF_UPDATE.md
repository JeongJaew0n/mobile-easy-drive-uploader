# GitHub Release 로 앱 안에서 업데이트하기 — 가능한가

2026-09-26 검토. **구현하지 않았다.** 할 수 있는지, 대가가 무엇인지만 적는다.

## 결론

**기술적으로는 된다. 다만 Play 배포를 포기해야 한다.** 둘은 같이 갈 수 없다.

이유가 둘이고, 각각 단독으로 치명적이다.

1. **Play 정책이 금지한다.** 자체 업데이트는 명시적으로 막혀 있고, 갤러리 앱은 예외 카테고리에 없다.
2. **서명이 맞지 않는다.** `docs/RELEASE.md` 대로 Play App Signing 을 쓰면, 사용자 기기의 앱은
   **Google 이 보관하는 키**로 서명돼 있다. 우리가 가진 것은 업로드 키뿐이라 같은 서명의 APK 를
   만들 수 없고, 서명이 다르면 설치가 거부된다.

그래서 이 기능은 **사이드로드 배포 전용**이다. 결정해야 할 것은 기술이 아니라 배포 경로다.

## 1. Play 정책 (확인: Play Console 정책 문서)

> "preventing abuse on the Android platform and protecting users from apps that self update
> using any method other than Google Play's update mechanism"

`REQUEST_INSTALL_PACKAGES` 를 선언할 수 있는 앱은 **패키지 설치가 핵심 목적**인 것들뿐이다 —
브라우저·검색, 첨부를 다루는 메신저, 파일 관리·전송, 기업용 기기 관리, 백업·복원, 기기 이전.
갤러리 백업 앱은 여기 없다. 선언하면 권한 신고서를 내야 하고, 승인되지 않으면 앱이 내려간다.

## 2. 서명 — 더 단단한 벽

정책은 배포처를 바꾸면 피할 수 있지만 서명은 그렇지 않다.

| 배포 | 기기의 앱을 서명한 키 | 우리가 서명할 수 있는 키 | 자체 업데이트 |
|---|---|---|---|
| Play (App Signing) | Google 의 앱 서명 키 | 업로드 키뿐 | **불가** |
| 사이드로드 | 우리 릴리스 키 | 같은 키 | 가능 |

Android 는 업데이트 시 **패키지명·서명이 모두 같아야** 설치를 허용한다. 하나라도 다르면
기존 앱을 지우고 새로 깔아야 하고, 그러면 앱 데이터(숨김 PIN·카테고리·자동 태그·업로드 원장)가
전부 사라진다. "업데이트" 라고 부를 수 없는 동작이다.

**지금 빌드로는 애초에 안 된다.** `keystore.properties` 가 없으면 릴리스 빌드가 디버그 키로
폴백한다. 디버그 키는 기기·개발자마다 다르므로 배포용으로 쓸 수 없다. 자체 업데이트를 하려면
진짜 릴리스 키를 만들고 **그 키를 잃어버리지 않는 것**이 전제다 — 잃으면 사용자는 앱을 지우고
다시 깔아야 하며, 그것 말고는 방법이 없다.

## 3. 사이드로드를 택했다면 — 어떻게 만드나

### 3-1. 새 버전 확인

저장소가 공개라 **인증 없이** 조회된다(확인함).

```
GET https://api.github.com/repos/JeongJaew0n/mobile-easy-drive-uploader/releases/latest
```

응답의 `tag_name` 을 `BuildConfig.VERSION_CODE` 와 비교한다. 버전은 태그 문자열이 아니라
**`versionCode` 정수**로 비교해야 한다 — `"0.10.0" < "0.9.0"` 같은 문자열 비교 사고를 막는다.
릴리스 본문이나 asset 이름에 versionCode 를 심고 그것을 읽는 편이 안전하다.

비인증 요청은 **IP 당 시간당 60회** 제한이다(확인함). 앱을 켤 때마다 묻지 말고 하루 한 번
정도로 충분하다. 실패해도 조용히 넘어가야 한다 — 업데이트 확인이 안 됐다고 갤러리를 못 쓰면 안 된다.

### 3-2. 내려받기

asset 의 `browser_download_url` 을 OkHttp 로 받아 `cacheDir` 에 쓴다. 이미 있는 것을 쓰면 된다.
크기가 수 MB 라 진행률이 필요하고, 화면을 벗어나도 이어지려면 WorkManager 가 맞다.

받은 파일은 **설치 전에 검증**한다. 릴리스에 SHA-256 을 함께 올리고 대조하는 정도면 충분하다.
HTTPS 만 믿기에는, 잘못된 APK 를 설치시키는 것의 대가가 크다.

### 3-3. 설치

`PackageInstaller.Session` 에 APK 바이트를 써 넣고 커밋한다. **무음 설치는 device owner
(기업용 관리 기기)만 가능하다.** 일반 앱은 시스템 설치 확인 화면이 뜨고 사용자가 누른다.
그 앞에 `REQUEST_INSTALL_PACKAGES` 권한과, 사용자가 설정에서 "이 출처 허용" 을 켜는 단계가 있다.

즉 흐름은 이렇게 된다.

```
[업데이트] → 확인 → 다운로드(진행률) → "알 수 없는 앱 설치 허용" (최초 1회)
           → 시스템 설치 화면 → 사용자가 [설치] → 앱 재시작
```

버튼 한 번으로 끝나지 않는다. 사용자에게 미리 그렇게 말해야 한다.

## 4. 위험

**삼성 기기.** Android 14 에서 Play 로 설치된 앱을 같은 키로 서명한 APK 로 덮으려 할 때
패키지 설치 관리자가 죽는 사례가 보고돼 있다. 우리 주 테스트 기기가 삼성 S23+ 와 Z Flip4 다.
구현한다면 **이것부터 실측**해야 한다.

**되돌릴 수 없다.** 설치가 반쯤 실패하면 사용자는 앱 없이 남는다. 다운로드 완료 후 검증에
성공한 뒤에만 설치를 시작하고, 실패하면 무엇을 해야 하는지(스토어/릴리스 페이지 링크) 알려야 한다.

**낮은 targetSdk 차단.** Android 14+ 는 targetSdk 가 너무 낮은 APK 설치를 막는다. 우리는 36 이라
문제없지만, 롤백용으로 옛 APK 를 설치하려 할 때 걸릴 수 있다.

## 5. 대안

| 방법 | 자체 업데이트 필요 | 비고 |
|---|---|---|
| **Play 내부 테스트 트랙** | 없음 | Play 가 업데이트를 맡는다. 테스터를 이메일로 등록. 지금 구조에 가장 잘 맞는다 |
| **Firebase App Distribution** | 없음 | 테스터에게 알림·설치. 서명은 우리 키. Play 와 별개 |
| **F-Droid** | 없음 | 공개 저장소·재현 가능 빌드가 전제 |
| GitHub Release + 자체 업데이트 | **있음** | 이 문서의 주제. 배포를 완전히 직접 통제하고 싶을 때 |

## 6. 권고

**지금은 만들지 않기를 권한다.** 이유는 셋이다.

첫째, 배포 경로가 아직 정해지지 않았다. Play App Signing 을 쓰겠다고 문서에 적어 두었는데
자체 업데이트를 만들면 그 결정을 뒤집게 된다. 순서가 거꾸로다.

둘째, 얻는 것에 비해 사용자가 겪는 것이 많다. "알 수 없는 앱 설치" 를 켜는 단계는 사용자에게
불안한 경험이고, 실제로 그 설정은 악성 앱의 주된 통로라 경고 문구도 그렇게 쓰여 있다.

셋째, 지금 필요한 것이 "테스터에게 새 빌드를 빨리 주는 것" 이라면 **Play 내부 테스트 트랙이나
Firebase App Distribution 이 같은 일을 더 적은 위험으로 한다.** 업데이트 설치는 OS 와 스토어가
맡고, 우리는 앱 코드를 건드리지 않아도 된다.

그래도 직접 배포를 택한다면, 순서는 이렇다.

1. 릴리스 키를 만들고 안전하게 보관한다 (이게 없으면 나머지가 의미 없다)
2. Play App Signing 을 쓰지 않기로 정하고 `docs/RELEASE.md` 를 고친다
3. 삼성 기기에서 "같은 키로 서명한 APK 로 덮어쓰기" 가 되는지부터 확인한다
4. 그 다음에 앱 안의 업데이트 흐름을 만든다
