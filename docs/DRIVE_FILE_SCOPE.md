# Drive `drive.file` — 좁은 권한으로 사는 법

앱이 기본으로 요청하는 Drive 권한은 `https://www.googleapis.com/auth/drive.file` 하나다.
(읽기 권한을 옵트인으로 더 받는 길이 §10 에 있다.)
전체 접근(`.../auth/drive`)은 restricted scope 라 스토어에 내려면 Google 보안 심사(CASA)를
받아야 하고, 사용자에게는 "내 Drive 전부를 이 앱이 본다"는 동의를 요구한다.
갤러리를 백업하는 앱에 그건 과하다.

대신 앱이 볼 수 있는 것이 크게 줄어든다. **이 문서는 무엇이 줄어드는지와,
그 제약 위에서 화면을 어떻게 짜는지를 적는다.**

## 1. 측정으로 확정된 제약

전부 2026-09-24 에 실기기에서 잰 것이다. 근거는 `docs/manual-tests/02-google-drive.md`
(DRV-P1~P6) 와 `docs/manual-tests/14-samsung-interop.md` (SS-09~11).

| 재본 것 | 결과 |
|---|---|
| 내 드라이브 루트 조회 | **빈 목록.** 사용자의 기존 파일·폴더가 하나도 보이지 않는다 |
| 앱이 만든 폴더·올린 파일 | 보인다 |
| 앱이 접근권을 가진 폴더 **안의 외부 파일** | **보이지 않는다.** 폴더 권한은 자식으로 상속되지 않는다 |
| 피커로 **폴더** 고르기 | **안 된다.** `PICKER_ALLOW_FOLDER_SELECTION="true"` 를 줘도 폴더는 탐색만 된다 |
| 피커로 고른 **파일**의 부모 폴더 | ID 는 읽힌다. 폴더 자체는 `files.get` **404** |
| 그 부모 폴더에 `files.create` | **된다.** 읽지 못하는 폴더에 쓸 수는 있다 |

마지막 두 줄이 이 설계의 핵심이다. **읽기와 쓰기의 경계가 다르다** — 폴더를 못 읽어도
그 폴더를 `parents` 로 지정한 생성은 통과한다.

## 2. 그래서 Drive 화면이 이렇게 된다

루트는 "내 드라이브의 자식들"이 아니라 **앱이 올릴 수 있는 폴더들**이다.

```
Google Drive
├── 여행 사진            ← 지정 폴더 (사용자가 별칭을 붙였다)
├── 2025 백업            ← 지정 폴더
├── Easy Gallery         ← 기본 폴더 (앱이 만든다)
└── 2019 앨범 [보기 전용]  ← 보기 폴더 (§10, 읽기 권한을 옵트인한 경우에만)
[+ 볼 수 있는 폴더 추가]
```

어느 폴더에 들어가든 **이 앱으로 올린 것만** 보인다. 이건 고장이 아니라 권한의 모양이므로,
화면이 그렇게 말해야 한다. 사용자가 Drive 앱에서 보던 파일이 우리 앱에서 사라진 것처럼
보이면 버그로 읽힌다.

## 3. 기본 폴더 — 지정한 곳이 없을 때

앱이 `Easy Gallery` 폴더를 만들고 거기에 올린다(`ensureAppRootFolder`). 앱이 만들었으므로
이름도 알고 안도 볼 수 있다. 아무것도 설정하지 않은 사용자가 기대하는 기본값이다.

## 4. 지정 폴더 — 이미 쓰던 폴더에 쌓고 싶을 때

피커가 폴더를 고르게 해주지 않으므로 **그 폴더 안의 파일을 하나 고르게** 한다.
고른 파일의 `parents` 가 우리가 원하는 폴더 ID 다.

```
"올리고 싶은 폴더 안의 파일을 아무거나 하나 고르세요"
  → 피커 → 파일 선택 → parents[0] = 폴더 ID
  → "이 폴더를 뭐라고 부를까요?"  (이름을 읽을 수 없어 사용자가 붙인다)
```

에두른 흐름이지만 이게 유일한 길이다. 화면에서 그 이유를 한 줄로 설명한다 —
"Google 이 폴더를 직접 고르게 해주지 않아, 그 안의 파일로 폴더를 지정합니다."

**빈 폴더는 지정할 수 없다.** 고를 파일이 없기 때문이다. 그 경우 기본 폴더를 쓰거나
Drive 앱에서 파일을 하나 넣고 오게 한다.

## 5. 저장

지정 폴더 목록은 `UserPreferencesRepository`(DataStore)에 직렬화해 둔다. Room 을 쓰지 않는
이유는 항목이 수십 개 수준이고 검색·조인이 필요 없어서다. 표를 하나 늘리는 값보다
마이그레이션 비용이 크다.

```kotlin
@Serializable
data class PickedFolder(val id: String, val alias: String)
```

## 6. 앱을 지웠다 깔면

OAuth 승인은 **계정 ↔ OAuth 클라이언트** 사이에 Google 서버가 기록한다. 앱을 지우는 것과는
다른 층이라, GCP 클라이언트가 그대로고 사용자가 계정에서 액세스를 취소하지 않았다면
파일별 접근권은 남는다. 사라지는 것은 **앱의 기억** — 어느 폴더를 지정했었는지다.

그래서 올릴 때 파일에 표식을 남긴다.

```kotlin
appProperties = mapOf("egTarget" to alias)
```

복구할 때는 표식이 있는 파일을 찾아 `parents` 를 모으면 폴더 ID 가, `egTarget` 값에서
별칭이 함께 돌아온다. **아직 아무것도 올리지 않은 지정 폴더는 되찾을 수 없다** —
표식이 될 파일이 없다. 그것만 다시 지정받는다.

주의: 클라이언트는 **패키지명 + SHA-1** 로 식별된다. 디버그 키와 릴리스 키는 다른 앱이라,
디버그로 올린 파일은 릴리스 빌드에서 보이지 않는다.

## 7. 권한이 끊겼을 때

게시 상태가 "테스트"인 앱은 발급된 토큰이 일정 기간 뒤 만료된다. 프로덕션으로 게시하기
전까지는 주기적으로 재동의가 필요하다는 뜻이다.

지금 코드는 `AuthorizationRequiredException` 을 문구로만 바꿔서, 한 번 끊기면 설정에서
연결 해제 후 재연결하는 것 말고는 빠져나갈 길이 없다(SS-11). 예외에 재동의
`PendingIntent` 를 실어 보내고 화면이 그것을 띄우게 고친다.

## 8. 이미 넓은 권한을 준 사용자

`setOptOutIncludingGrantedScopes(true)` 를 주지 않으면 계정에 남은 이전 `drive` 동의가
누적돼 토큰이 `[drive.file, drive]` 로 온다(SS-10). 앱이 요청을 좁혀도 실제 권한은
좁아지지 않는다. 모든 authorize 요청에 이 플래그를 준다.

그래도 **이미 동의한 권한 자체를 앱이 회수할 수는 없다.** 계정 연결 페이지에서 사용자가
직접 지워야 한다. 안내 문구로만 다룬다.

## 9. 범위 밖

- 피커로 폴더를 직접 고르기. Google 이 지원하면 §4 의 에두른 흐름을 걷어낸다.

## 10. 보기 전용 폴더 — 읽기 권한을 옵트인으로 받는다

2026-09-26 추가. 계획은 `docs/plans/drive-view-folders/spec.md`.

§1 대로 `drive.file` 로는 **남의 폴더 안을 볼 수 없다.** 그런데 "내 Drive 의 다른 폴더도
앱에서 보고 싶다" 는 요구는 남는다. 이건 코드로 우회할 수 있는 문제가 아니라 권한의 크기다.

그래서 **`drive.readonly` 를 추가로**, 그러나 **처음부터는 받지 않는다.**

```
기본 설치            : [drive.file]                      ← 동의 화면 그대로
"볼 수 있는 폴더 추가" : [drive.file, drive.readonly]      ← 이때 한 번 더 묻는다
```

### 10.1 왜 옵트인인가

`drive.readonly` 는 restricted scope 다. Play 프로덕션 공개 시 CASA 보안 심사를 부른다.
기본으로 요구하면 이 기능을 안 쓰는 사용자까지 그 비용을 지고, 동의 화면도 무거워진다.
옵트인이면 **버튼 하나를 내리는 것으로 되돌릴 수 있다** — 구조를 다시 짤 필요가 없다.

### 10.2 토큰에 scope 를 빠뜨리지 않기

`setOptOutIncludingGrantedScopes(true)`(§8) 때문에 **요청하지 않은 scope 는 토큰에 실리지
않는다.** 동의를 받아 놓고 토큰 요청에서 빼먹으면 보기 폴더가 조용히 빈 목록이 된다.
`GoogleAuthRepository.requestedScopes()` 가 옵트인 플래그를 읽어 매번 채운다.

동의 화면에서 사용자가 읽기 권한만 체크를 풀 수 있으므로, 결과의 `grantedScopes` 에
실제로 들어왔는지 **확인한 뒤에** 플래그를 켠다.

### 10.3 두 목록은 성격이 반대다

| | 지정 폴더 `PickedFolder` | 보기 폴더 `ViewFolder` |
|---|---|---|
| 올리기 | **된다** | 안 된다 |
| 안을 보기 | 이 앱으로 올린 것만 | **전부 보인다** |
| 이름 | 읽을 수 없어 사용자가 붙인 별칭 | Drive 에서 그대로 |
| 필요한 권한 | `drive.file` | `drive.readonly` |

루트 목록은 올릴 수 있는 것(지정 → 기본)이 먼저, 보기 전용이 뒤다. 보기 전용 행에는
"보기 전용" 이 붙고, ⋮ 에는 **"목록에서 제거"** 하나만 있다 — Drive 의 폴더는 건드리지 않는다.

### 10.4 안쪽으로 들어가도 읽기 전용

`DriveBrowserKey.readOnly` 가 한 번 true 가 되면 더 깊이 들어가도 계속 true 다.
읽기 권한은 안쪽으로 갈수록 넓어지지 않는다. 화면은 이 값으로 `Capability` 집합에서
`RENAME`·`MOVE`·`TRASH`·`FOLDER_MUTATION` 을 빼고, 업로드 폴더 지정 버튼도 감춘다.

**다운로드는 남긴다.** 읽기 권한으로 되는 일이고, 남의 폴더 사진을 기기로 가져오는 것이
이 기능을 쓰는 이유이기도 하다.

### 10.5 폴더 고르기는 에두르지 않는다

읽기 권한이 있으면 폴더를 **읽을 수 있으므로** §4 의 "폴더 안의 파일을 하나 고르세요" 가
필요 없다. 이동 대상 고르기에 쓰던 `DriveFolderPickerSheet` 를 그대로 써서 내 드라이브부터
탐색한다. 최상위(`root`) 자체는 고를 수 없다 — 그건 폴더가 아니라 최상위다.

### 10.7 검색도 함께 넓어진다 — 그래서 읽기 전용이다

읽기 권한을 받으면 `files.list` 가 Drive 전체를 훑는다. 검색 결과에 **앱이 쓸 수 없는
남의 파일이 섞인다.** 처음에는 그 파일에도 이름 변경·휴지통 메뉴가 그대로 떴다(DRV-46).
누르면 403 이다.

어느 결과를 쓸 수 있는지 앱은 알 길이 없다. Drive 가 주는 `capabilities.canEdit` 은
**사용자** 기준이지 우리 토큰 기준이 아니다. 그래서 읽기 권한을 옵트인한 사용자의
**검색 결과는 통째로 읽기 전용**으로 둔다(`DriveBrowserUiState.isReadOnlyHere`).

옵트인하지 않은 사용자에게는 달라지는 것이 없다 — 검색 결과가 원래 앱이 쓸 수 있는
파일뿐이다.

### 10.8 같은 폴더가 두 목록에 들어가면

지정 폴더(또는 기본 폴더)를 보기 폴더로도 추가하면 루트에 같은 id 가 두 번 들어가
**LazyColumn 이 죽는다**(`Key ... was already used`, DRV-48). 두 겹으로 막았다.

- `rootEntries()` 가 이미 있는 id 를 걸러낸다. 올릴 수 있는 쪽을 남긴다 — 그쪽이 할 수 있는 일이 많다.
- 추가하는 순간에도 목록을 보고 "이미 목록에 있습니다" 로 되돌린다.

### 10.6 사람이 해야 하는 일

**GCP OAuth 동의 화면에 `drive.readonly` 를 등록해야 한다.** 등록되지 않은 scope 를
요청하면 authorize 가 실패한다. 코드만으로는 안 되는 단계다.

계정 연결을 끊으면(`clearAccount`) 보기 폴더 목록과 옵트인 플래그도 함께 지운다 —
폴더 ID 는 계정에 종속된 값이다.
